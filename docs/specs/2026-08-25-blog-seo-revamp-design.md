## 3. 스택과 배포

**Astro 7 + TypeScript**, GitHub Actions 빌드 → GitHub Pages 배포.

- 콘텐츠는 `.md`/`.mdx` 원본 유지, Astro **Content Collections**로 프론트매터 스키마 검증
  - `description` 필수화 → D5를 빌드 타임에 강제
  - `section` / `hub` / `type` / `level` / `date` / `tags` 필드 타입 검증 → D12 재발 방지 (§6, §8)
- Ruby 의존성 완전 제거 (로컬 빌드 불가 상태 해소)
- 코드 하이라이팅: Shiki (빌드 타임, 런타임 JS 0)
- jQuery 제거 (D8)

## 4. URL 보존 — 최우선 제약

`/:year/:month/:day/:title/` 구조를 **1:1로 재현**한다. 146개 URL 중 하나라도 바뀌면 백링크와 색인이 손실된다.

**검증 게이트**: 마이그레이션 후 아래가 통과해야 다음 Phase로 진행한다.

```
기존 sitemap.xml의 URL 집합 − 신규 빌드 산출물의 경로 집합 = ∅
```

자동화 테스트로 구현하며, 이 테스트 실패 시 배포를 막는다.

동일 경로 유지 대상: `/feed.xml`, `/rss2.xml`, `/sitemap.xml`, `/ads.txt`, `/robots.txt`, `/404.html`

## 5. 사이트 아이덴티티와 SEO 메타 재설계

### 5.1 현재 메타의 문제

```yaml
title: CodeNexus
description: Software Engineering Tech Blog   # 영어
author.name: CodeNexus                        # 유지 (브랜드 명의 발행)
hero__title: Hi! I'm <span>Andrew</span>      # 영어, 정보량 0
hero__job: BackEnd Developer
```

두 가지가 잘못돼 있다.

1. **description이 영어**인데 타깃 독자는 한국어 검색자다. 검색 스니펫에 노출될 키워드가 하나도 없다.
2. **hero 카피에 정보가 없다.** "Hi! I'm Andrew"는 검색에도 사용자 판단에도 기여하지 않는데 모든 포스트 최상단을 차지한다(D6). 게다가 개인 식별 정보를 노출한다(§7 참조).

`author: CodeNexus`는 그대로 둔다. 개인이 아닌 **브랜드 명의 발행**으로 가는 것이 §7의 결정과 일치한다.

### 5.2 사이트명

**확정: `CodeNexus` 유지.** 브랜드 검색량은 미미하나 이미 3년치 인용·북마크가 이 이름으로 존재하므로, 변경 이득보다 혼란 비용이 크다. 대신 **모든 메타 카피를 한국어 키워드 중심으로 전면 교체**해서 실질 효과를 얻는다. 사이트명 자체보다 description·h1·소개글의 한국어 키워드화가 유입에 훨씬 크게 작용한다.

### 5.3 title 태그 규칙

구글 SERP는 한국어 기준 약 30~35자에서 절단된다. **앞 30자 안에 핵심 키워드**를 배치한다.

| 페이지 | 템플릿 | 예시 |
|---|---|---|
| 홈 | `{한국어 주제구} \| {사이트명}` | `백엔드 · 아키텍처 · AI 기술 블로그 \| CodeNexus` |
| 포스트 | `{글 제목} \| {사이트명}` (제목 30자 초과 시 사이트명 생략) | `JPA 연관관계 매핑 완전 정리 \| CodeNexus` |
| 섹션 | `{섹션} \| {사이트명}` | `아키텍처 \| CodeNexus` |
| 허브 | `{주제} 정리 — {부제} \| {사이트명}` | `Spring Boot 정리 — 입문부터 실무까지 30편 \| CodeNexus` |
| 태그 | `{태그} 관련 글 {n}편 \| {사이트명}` | `Redis 관련 글 3편 \| CodeNexus` |
| 다이제스트 | `AI · 개발 위클리 {n}호 ({날짜}) \| {사이트명}` | `AI · 개발 위클리 12호 (2026-09-01) \| CodeNexus` |

**금지**: 사이트명을 title 앞에 두는 것(`CodeNexus - JPA 연관관계...`). 절단 시 핵심 키워드가 잘린다.

### 5.4 description 규칙

한국어 기준 **앞 78자 이내에 핵심**을 넣고 전체는 150자 이내.

- **홈**
  ```
  아키텍처 · 백엔드 · 데이터 · AI를 다루는 한국어 기술 매체. Spring, JPA, Java,
  MySQL 실무 예제와 트러블슈팅을 정리하고 매주 AI · 개발 뉴스를 큐레이션합니다.
  ```
- **포스트**: 글마다 수기 작성. 규칙 —
  1. 첫 문장에 검색어(= 글의 핵심 키워드)를 그대로 포함
  2. "무엇을 알게 되는가"를 명시 (`~하는 방법`, `~의 차이`, `~ 주의점`)
  3. 본문 첫 문단 복붙 금지 (스니펫 중복 방지)
- **허브**: 그 주제로 몇 편이 있고 어떤 순서로 읽으면 되는지 명시
- Content Collections 스키마에서 `description` 필수 + 20~150자 길이 검증

현재 제목의 구체적 문제와 처리:

## 6. 정보구조(IA)와 전역 메뉴 재설계

### 6.0 설계 목표 전환

기존 146편의 태그 분포를 그대로 메뉴로 옮기면, 사이트가 **"지금까지 쓴 것"에 갇힌다.** 새 주제를 쓸 때마다 메뉴를 뜯어고쳐야 하고, 그때마다 URL과 내부링크 구조가 흔들린다.

따라서 순서를 뒤집는다. **확장 가능한 분류 체계를 먼저 세우고, 기존 146편을 그 안에 채워 넣는다.** 비어 있는 칸은 앞으로 채울 자리이지 결함이 아니다.

벤치마크는 개인 블로그가 아니라 기술 매체의 IA다(InfoQ: Development / Architecture & Design / AI·ML & Data / DevOps / Culture & Methods).

### 6.1 설계 원칙

1. **2단 분류.** 최상위 섹션(변하지 않음) + 하위 허브(자유롭게 추가). 새 주제는 하위 허브만 추가하면 되고 최상위는 건드리지 않는다.
2. **최상위는 7개 이하.** 전역 메뉴 링크는 모든 페이지에서 반복되는 가장 강한 내부링크 신호다. 개수를 늘리면 신호가 희석된다.
3. **모든 메뉴 항목은 pillar 페이지.** 단순 목록이 아니라 그 주제를 개괄하는 본문을 가진다.
4. **앵커 텍스트는 검색 키워드 그대로.** `개발`, `기타` 같은 모호어 금지.
5. **JS 없이 크롤 가능.** CSS-only 드롭다운.
6. **빈 섹션은 색인시키지 않는다.** §6.4의 단계적 오픈 규칙.

### 6.2 최상위 섹션 (7개)

| 섹션 | URL | 성격 | 현재 자산 | 확장 여지 |
|---|---|---|---|---|
| 아키텍처 | `/architecture/` | 시스템 설계·분산·성능·패턴 | 거의 없음 | **최대**. 연차가 쌓일수록 쓸 게 많고, 검색 수요·체류시간·광고 단가가 모두 높은 영역 |
| 백엔드 | `/backend/` | Spring · JPA · Java · 테스트 | **~67편** | 기존 최대 자산 |
| 웹 · 프론트엔드 | `/web/` | JavaScript · TypeScript · Node.js | ~30편 | 중 |
| 데이터 | `/data/` | MySQL · Redis · 쿼리 튜닝 · 데이터 모델링 | ~15편 | 중 |
| 인프라 · DevOps | `/infra/` | Docker · AWS · CI/CD · 관측성 | ~10편 | 중 |
| AI · LLM | `/ai/` | LLM 활용 · AI 코딩 · RAG · 에이전트 | **0편** | **최대**. 신규 성장축 |
| 뉴스 | `/news/` | 주간 다이제스트 · 릴리스 트래킹 | 0편 | 신규 |

개발 도구(IntelliJ · Mac · 터미널 · Git, ~20편)는 최상위로 올리지 않고 `/infra/tools/` 하위 허브로 둔다. 편수는 있으나 검색 유입의 질이 낮고 최상위 7칸을 쓸 만큼의 전략적 가치는 없다.

### 6.3 하위 허브

### 6.4 단계적 오픈 규칙 (thin content 방지)

빈 껍데기 허브를 색인시키면 사이트 전체 품질 평가가 내려간다. 확장성을 위해 구조는 미리 만들되, 노출은 콘텐츠 양에 연동한다.

| 글 수 | 메뉴 노출 | 색인 | 처리 |
|---|---|---|---|
| 0편 | ❌ 노출 안 함 | — | 라우트만 정의, 빌드 산출물 없음 |
| 1~2편 | 상위 섹션 페이지 안에만 표시 | `noindex, follow` | 허브 페이지는 생성하되 색인 제외 |
| **3편 이상** | ✅ 드롭다운 노출 | `index` | 정식 허브. 리드 문단·학습 순서 작성 필수 |

이 규칙은 **빌드 타임에 자동 적용**한다. 글을 추가하면 임계를 넘는 순간 허브가 자동으로 열리므로 수동 관리가 필요 없다. 즉 `/ai/`, `/architecture/`는 지금은 닫혀 있고, 글을 3편 쓰면 스스로 열린다.

`/news/weekly/`는 예외로 Phase 5에서 첫 호 발행과 동시에 오픈한다.

### 6.5 전역 메뉴 최종 형태

```
┌────────────────────────────────────────────────────────────────────────┐
│  CodeNexus    아키텍처   백엔드 ▾   웹   데이터   인프라   AI   뉴스     │
│                                                        [🔍]  소개      │
└────────────────────────────────────────────────────────────────────────┘
                    │
                    └── 드롭다운 (CSS only, 크롤 가능)
                        Spring · Spring Boot     30편
                        JPA · Hibernate          19편
                        Java 언어                13편
                        테스트                     5편
```

- 드롭다운에는 **오픈 임계를 넘은 하위 허브만** 표시하고 글 수를 함께 노출한다(사용자에게는 깊이의 신호, 크롤러에게는 구조 신호)
- 모바일은 햄버거 → 섹션별 아코디언. `<details>` 요소로 구현해 JS 없이 동작하고 크롤 가능
- 최상위 섹션 라벨을 클릭하면 드롭다운을 열지 않고 섹션 pillar 페이지로 이동(모바일은 아코디언 토글)

### 6.6 두 번째 분류축 — 콘텐츠 유형

주제(§6.2)만으로는 "Spring 30편" 안에서 입문 글과 트러블슈팅 기록이 뒤섞인다. 전문 매체의 밀도를 내려면 **주제 × 유형의 2차원 분류**가 필요하다.

| 유형 | 뱃지 | 성격 | 검색 의도 |
|---|---|---|---|
| 튜토리얼 | 🟢 | 따라 하면 되는 것 | `~하는 방법`, `~ 예제` |
| 레퍼런스 | 🔵 | 문법·API 사용법 | `~ 사용법`, `~ 옵션` |
| 트러블슈팅 | 🟠 | 문제와 해결 | `~ 에러`, `~ 안 될 때` |
| 딥다이브 | 🟣 | 내부 동작 원리 | `~ 원리`, `~ 동작 방식` |
| 뉴스 | ⚪ | 다이제스트 | — |

- 프론트매터 `type` 필드로 관리하고, 목록·허브에서 필터링
- 허브 페이지에서 **"입문 → 실무 → 심화" 학습 순서**를 만들 때 이 축을 사용한다
- 별도 URL을 만들지 않는다(색인 대상 아님). 조합 페이지를 색인하면 중복 콘텐츠가 된다

### 6.7 난이도

프론트매터 `level` (`입문` / `중급` / `심화`). 목록에 표시하고 허브의 학습 순서 정렬 기준으로 쓴다. §6.6과 마찬가지로 별도 URL은 만들지 않는다.

### 6.8 허브 페이지 구성 (pillar page)

각 허브는 단순 글 목록이 아니다. 이것이 topical authority의 실체다.

```
h1: {주제} 정리 — {부제}
├─ 리드 문단 (200~300자): 이 주제가 무엇이고 이 페이지에서 무엇을 얻는지
├─ 📚 학습 순서 (입문 → 실무 → 심화)   ← 순서가 있는 내부링크 = 가장 강한 신호
│   1. 영속성 관리                  🟣 딥다이브 · 입문
│   2. 엔티티 매핑                  🔵 레퍼런스 · 입문
│   3. 연관관계 매핑 기초            🟢 튜토리얼 · 중급
├─ 주제별 섹션 (h2)
│   h2: 연관관계 매핑    → 관련 글 5편
│   h2: 성능과 최적화    → 관련 글 4편
├─ 자주 묻는 질문 (FAQ)  ← FAQPage 스키마 대상
└─ 전체 글 목록 (최신순, 유형·난이도 필터)
```

최상위 섹션 페이지(`/backend/` 등)는 하위 허브를 소개하고 각 허브의 대표 글 3편씩을 노출하는 라우팅 페이지로 만든다.

### 6.9 그 외 내비게이션

- **푸터**: 최상위 7섹션 + 오픈된 하위 허브 전체 + 태그 클라우드 + RSS + 소개
- **브레드크럼**: `홈 › 백엔드 › JPA › 글 제목` (BreadcrumbList 스키마 연동, 2단 구조를 그대로 반영)
- **관련 글**: 같은 허브·태그 기준 3~5편 자동 렌더
- **시리즈 내비**: 순서가 있는 글(`JPA - 영속성 관리(1)` ~ `(6)`)은 이전/다음으로 연결
- **hero 제거**: 포스트 페이지에서 hero를 걷어내고 본문을 최상단으로 (D6)
- **사이트 내 검색**: Pagefind(빌드 타임 정적 인덱스, 서버 불필요). `WebSite.SearchAction` 스키마와 연동

### 6.10 태그 정책 (D10, D12 해소)

허브가 주제의 뼈대라면 태그는 그 사이를 가로지르는 보조축이다(`docker`, `mac`, `성능`처럼 여러 허브에 걸치는 것).

- 태그당 글이 **3편 이상**이고 **설명문이 작성된** 태그만 `index` 허용
- 나머지는 `noindex, follow`
- `robots.txt`의 `Disallow: /tag/` 제거, 페이지 단위 메타로 제어
- 마이그레이션 시 제목·본문 기반으로 **누락 태그 일괄 보정** (JS 계열 30편 등, D12)
- 기존 커밋된 `tag/*/index.html` 87개는 삭제하고 Astro가 생성

## 7. 소개(About) 페이지 재설계

### 7.0 개인정보 비노출 원칙 (사용자 확정)

**운영자 개인을 식별할 수 있는 정보를 사이트 어디에도 노출하지 않는다.** 실명, 활동명(`Andrew` 포함), 경력 연차, 소속, 프로필 사진, 개인 이메일, 개인 소셜 프로필 전부 해당한다.

따라서 사이트를 **개인 블로그가 아니라 `CodeNexus`라는 브랜드 명의의 기술 퍼블리케이션**으로 재정의한다. 이 방향은 §5.2(사이트명 유지)와도 일치한다.

#### 제거 대상 (실측 확인된 노출 지점)

| 노출 지점 | 위치 | 처리 |
|---|---|---|
| `Hi! I'm <span>Andrew</span>` | `_config.yml:19` hero 카피 | 삭제 → §7.2 카피로 교체 |
| `BackEnd Developer` | `_config.yml:20` | 삭제 |
| 프로필 사진 `/images/01.jpg` | `_config.yml:15`, `_config.yml:23` | 사이트에서 미사용. 로고/OG 이미지로 대체 |
| 개인 Gmail `umanking@gmail.com` | `_config.yml:47` | 노출 중단 (§7.4) |
| buymeacoffee `slug=umanking` | `_includes/side-menu.html` | 후원 버튼 제거 (개인 계정 식별) |
| 회고성 포스트 3편 | `[회고] 2020년 상반기`, `[회고] 2021년 상반기`, `[월간리뷰] 2021년 7월` | **본문 내 개인 정보 점검 필요** — §7.5 |

#### 감수하는 손실

Google은 기술·실용 콘텐츠에서 저자의 경험과 전문성(E-E-A-T)을 평가하며, 익명 브랜드는 실명 저자보다 이 신호가 약하다. 이를 보완할 수 있는 것은 **콘텐츠 자체의 신뢰 신호**뿐이므로 다음으로 대체한다.

- 예제 코드의 실행 환경·버전 명시 (`Spring Boot 3.2 / Java 21 기준`)
- 글마다 발행일과 **수정일** 노출 (git 커밋 기반, §5.7)
- 출처·공식 문서 링크 인용
- 오류 정정 이력 표기

#### 남는 한계 (제거 불가)

`umanking.github.io` 도메인을 유지하는 한 `umanking` 문자열은 URL에 남는다. GitHub Pages 사용자 사이트는 계정명이 곧 주소이고, utterances 댓글도 저장소에 연결된다. **완전 익명은 커스텀 도메인 없이는 불가능하다.** 이것이 문제라면 §2의 도메인 결정을 재검토해야 한다.

### 7.1 About 페이지의 역할 재정의

`/about`이 지금 404라는 건(D2) 단순한 빠진 페이지가 아니다. `_config.yml:22`의 히어로 버튼이 이 URL을 가리켜 사이트 전체에 깨진 링크가 반복 노출되고, §6의 7개 섹션을 한자리에 모아 링크를 흘려보낼 페이지도 없다.

About을 **자기소개가 아니라 매체 소개 + 섹션 안내**로 만든다.

```
h1: CodeNexus 소개

▸ 리드 문단
  "CodeNexus는 아키텍처 · 백엔드 · 데이터 · AI를 다루는 한국어 기술 매체입니다.
   실무에서 마주친 문제와 해결 과정을 기록하고, 매주 AI · 개발 뉴스를
   큐레이션합니다. 2019년부터 146편을 발행했습니다."

h2: 다루는 주제                       ← 이 페이지의 핵심
  - 7개 섹션 + 오픈된 하위 허브 전체로 내부링크, 각각 한 줄 설명
  - 아키텍처 / 백엔드 / 웹 / 데이터 / 인프라 / AI / 뉴스

h2: 분류 체계 안내
  - 유형(튜토리얼·레퍼런스·트러블슈팅·딥다이브)과 난이도 표기 설명 (§6.6, §6.7)

h2: 글을 쓰는 원칙
  - 실무에서 직접 겪은 문제와 해결 과정을 기록한다
  - 예제 코드는 실행해 보고 올리며, 실행 환경과 버전을 명시한다
  - 오류가 확인되면 본문을 수정하고 수정일을 표기한다
  - AI 위클리 다이제스트는 자동 수집한 초안을 **직접 검토·편집해서** 발행한다
    ← 애드센스 정책(Scaled Content Abuse) 방어 겸 독자 신뢰 신호

h2: 정정 · 제보                        ← 각 글 댓글로 안내 (§7.3)
```

**저자 박스는 만들지 않는다.** 포스트 하단에는 저자 대신 발행일·수정일·출처·관련 글을 배치한다.

### 7.2 홈 히어로 카피 교체

| 현재 | 개선 |
|---|---|
| `Hi! I'm Andrew` / `BackEnd Developer` | h1: **`백엔드 · 아키텍처 · AI 기술 블로그`**<br>부제: `실무에서 마주친 문제와 해결 과정을 한국어로 기록합니다. Spring · JPA · 데이터 · 인프라 146편과 매주 AI · 개발 뉴스 큐레이션.` |

홈 h1은 사이트 전체 주제를 선언하는 자리다. 인사말이 아니라 키워드가 들어가야 한다.

### 7.3 연락 수단

**확정: 연락처를 노출하지 않는다.** 개인 Gmail(`_config.yml:47`)은 내리고, 별도 창구도 두지 않는다.

감수하는 리스크:
- 정정·저작권 문의를 받을 통로가 없다
- 광고 게재 사이트에 연락 수단이 없는 것은 신뢰도 측면에서 소폭 불리하다

**완화 장치**: 댓글(utterances)이 사실상 유일한 피드백 경로가 되므로, 포스트 하단 댓글 영역을 접근성 있게 배치하고 About에 "정정 제보는 각 글의 댓글로"라고 명시한다. 나중에 전용 이메일을 만들기로 하면 About의 문의 섹션만 추가하면 되도록 설계해 둔다.

### 7.4 기존 포스트 개인정보 점검

마이그레이션 전에 146편 전체를 대상으로 아래를 스캔하고, 검출된 항목은 사용자 확인 후 처리한다.

- 이메일 주소, 실명, 사번, 회사·팀명
- 개인 프로필 사진, 사내 스크린샷, 사내 URL·IP·호스트명
- 회고성 글 3편의 개인 신상 서술

**처리 방침은 글마다 사용자가 결정한다** — 해당 문장만 수정 / 글 전체 비공개(`noindex` + 목록 제외) / 삭제. 삭제 시 URL이 사라져 §4의 URL 보존 원칙과 충돌하므로, 삭제보다 **수정 또는 비공개**를 우선한다.

## 9. 애드센스

`ca-pub-2431823363518805`와 `ads.txt`를 그대로 유지한다(재승인 불필요).

- `_includes`의 광고 include 4개(`google-adsense`, `google-adsense2`, `google-adsense-feed`, `google-adsense-infeed`)를 **컴포넌트 1개로 통합**

- `ban-adblock.html`은 사용자 경험 저해 소지가 있어 제거 검토

## 10. AI · 개발 위클리 다이제스트 파이프라인

```
GitHub Actions (주 1회 cron)
  ↓ 소스 수집
    Hacker News API / arXiv cs.AI / GitHub Trending
    Anthropic · OpenAI · Google 공식 블로그 RSS
  ↓ Claude API로 후보 선별 + 한국어 초안 생성 (백엔드 개발자 관점)
  ↓ Pull Request 생성          ← 자동 커밋 아님
  ↓ 사용자가 "왜 중요한가" 코멘트 추가 후 머지
  ↓ 발행
```

**PR 게이트가 정책 방어의 핵심이다.** 사람 검토 없이 발행되는 경로를 아예 만들지 않아야 Google의 Scaled Content Abuse 판정을 피할 수 있다.

초안 구성 원칙:
- 원문 요약이 아니라 **"이번 주에 무슨 일이 있었고, 백엔드 개발자 입장에서 무엇이 달라지나"**
- 원문 출처를 항목마다 명시 링크
- 발행 빈도 주 1~2회 상한

## 11. 디자인 방향

기성 테마 없이 직접 구현한다.

- 한글 가독성 우선: Pretendard(서브셋), 본문 17px / 행간 1.8 / 최대폭 680px
- 라이트·다크 자동 감지 + 토글, 시스템 설정 존중
- Shiki 코드 하이라이팅 + 파일명 라벨 + 복사 버튼
- 스티키 TOC (데스크톱), 읽기 진행 바
- 읽기 시간·발행일·수정일 표시
- **유형·난이도 뱃지** (§6.6, §6.7) — 목록·허브·포스트 상단
- **브레드크럼** — 2단 IA를 시각적으로 드러내 사이트 규모를 인지시킨다
- 광고가 들어가도 정돈돼 보이는 여백 설계
- 댓글은 기존 utterances 유지 (저장소 소유자 노출은 §7.0의 감수 범위)

전문 매체의 인상은 장식이 아니라 **밀도와 일관성**에서 나온다. 모든 목록 항목이 제목·요약·유형·난이도·날짜·읽기시간을 동일한 형식으로 갖추는 것이 화려한 애니메이션보다 효과가 크다.
